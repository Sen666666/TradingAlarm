# v2 冻结交付，等待另一任务独审

本轮已落实主任务对 pending_price_failure 的明确裁决，合同、源码及合成验证冻结于本 v2-frozen 目录。父目录 v1 的合同、源码、输出和哈希保持原样。历史 FSM 输出、账户、下载、下单、交易服务操作及原项目修改均为0。

具体变化：已知价格触及旧线但广度未知时，保存不可改写的 PriceFailure 日志，失败只计一次，立即撤销许可；旧线、锚、前沿退役，修复信用为0。等待期间没有修复锚或信用，不利用未知期间低点。第一条后续价格、广度及此前因果尺度都已知的观察，仅前向分类：正广度用当前价和当前尺度创建 REPAIR 锚，非正广度 ENDED。分类当次信用0，即使原 BREAK 为真也不能重启或恢复。失败时广度永远为 None，后来的正广度不回填历史。

换源清除待判上下文、重新暖机等待新 BREAK，同时保留完整失败日志。按最新裁决“触及旧线”，已知与未知广度价格失败统一为 close <= old_line；v1 的严格小于比较保留。这是明确的比较边界修正，没有查看历史候选结果。

32 项合成测试通过。八个原物理前缀加十五个 pending 物理前缀，共23个新进程前缀；13个 pending 磁盘 checkpoint 新进程恢复；219个 JSON 保存恢复切点。测试覆盖未分类等待、首条完整观察的正／非正分类、缺价格／缺广度／缺尺度、等待低点无信用、分类当次 BREAK 优先级、日志不可改写、换源终止、后续新推进恢复及原全部要求的正反例。

接口必须看清：四状态 mode 的 REPAIR 槽承载一个无锚 pending 阶段，pending_price_failure 标志拥有最高转移优先级；effective_status 明示 PENDING_PRICE_FAILURE，完全跳过普通 REPAIR 积信用逻辑。它不是已确认正广度的修复。消费者只能用 permit_next_open 作为风险开关。

其他未知边界均已在 CONTRACT.md 第5节明确：普通已锚定 REPAIR 遇未知广度仍观察价格，但不授予许可；未知价格不产生收益或信用；普通 REPAIR 的已知弱广度可立即结束，而 pending 必须等一条价格、广度、尺度完整的观察；换源优先；缺失一直持续就一直等待，不加超时门。当前没有未定义的未知转移。手工损坏的普通 ACTIVE／REPAIR checkpoint 不属于合法状态；loads 负责本程序状态恢复及关键 pending 一致性，不是完整外部反序列化安全边界。
