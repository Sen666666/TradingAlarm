# Event-specific Q0 factor-only proof, independently scoped and disabled

For a new simulated account initialized solely with cash, no predecessor positions and no inherited claims/receivables, complete account-lifetime evidence that this security was never owned up to an ordinary-cash ex-date proves zero entitlement. Under the explicit ordinary-cash semantics that record-date ownership determines entitlement and record date precedes ex-date, every possible record snapshot is zero, even without knowing the exact record/payment date. This is not a theorem about an existing real account.

Runtime proof must establish complete ordered ledger coverage from inception, no positive-quantity orders/holdings, no archive round/current position, no positive record snapshot, no claim even if paid, and no entitlement cash/receivable/quantity evidence. The exact named source event must independently be PURE_CASH,split1,correct exdate/source identity and exact factor bridge. A previously held security fails even if currentlyflat. Later events require a new proof; a stock cannot receive a future blanket exemption. A newly acquired ex-date position does not inherit an earlier unknown record-date entitlement.

Proof does not manufacture record/pay dates, dividend amounts, receivables or cash. It establishes only that this exact event cannot create an entitlement in this new simulation. An executable factor-only adapter would need a separate registry, never an incomplete entry in cash d.events; it must integrate factor/action preflight, retained and paused quote-gap chain validation, diagnostics and any reference-price gate, with whole-day rollback. Existing cash consumers require record/pay fields and must stay unchanged.

q0_factor_only_proof.py is a pure checker with no engine integration or writes. Current v5 cash batch does NOT enable this fallback: targeted official-source completion has supplied dates for all14November-December missing-date candidates, so the ordinary19-event cash batch is preferred. Any later activation needs exact-event manifest, explicit input-validation contract, independent tests and approval. If proof fails, remain blocked; no unknown-payment guess or new receivable-only scenario.
